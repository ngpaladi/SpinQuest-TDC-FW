Board state01

A cold power-up lands at a login prompt with the fabric programmed and both network ports up, needing no keyboard and no network. The stages below are what gets you there, in the order they run.

StageContentsStatus
QSPIFSBL + PMUFW + BL31 + patched DTB + U-Boot (1.7 MB)verified
eMMC p1FAT32 · Image, system.dtb, boot.scrverified
eMMC p2ext4 root, 13.5 GB, persistentverified
PL fabricTDC bitstream, loaded at boot by tdc-fpga.service (134 ms)verified
Ethernet2 × 1 GbE, factory MACs, 0.94 Gbps/port measuredverified
PCIe EPEndpoint configured; link stalls in Detect/Pollingblocked

Log in as petalinux with the password set on first boot. SSH is enabled and each port takes its own DHCP lease, so the board is reachable on either one.

Boot image composition02

The boot image is assembled from more than one source, and the mix matters. Substituting either the FSBL or U-Boot for the one you would reach for first produces an image that boots to complete silence — no banner, no error — so it is worth understanding why each partition comes from where it does.

PartitionSourceWhy this one
FSBLThis project's PetaLinux buildPrograms the KrIO pinmux. AMD's stock K26 FSBL programs the KV260 pinmux (GEM3) and silently kills MDIO.
PMUFW, BL31This project's build—
DTB @0x100000This project, patchedU-Boot reads its control DTB from here.
U-BootExtracted from the original working imageHas a working sf layer. The PetaLinux-built U-Boot honours stdout-path = serial1 → /dcc and prints to the JTAG debug channel — it runs fine and looks dead.
BitstreamLoaded at runtime by LinuxKeeps the QSPI image under the ~2 MB JTAG ceiling; new firmware is a file copy, never a reflash.
JTAG ceiling

Vivado's program_hw_cfgmem and Xilinx's program_flash both hang indefinitely on images larger than roughly 2 MB when the board is in QSPI boot mode. Rather than fight this, we keep the QSPI image small and let the board flash itself over TFTP, which writes 9.5 MB in about 70 seconds. JTAG stays as the recovery path.

tftpboot 0x10000000 BOOT.BIN
sf probe
sf update 0x10000000 0 ${filesize}

Device tree requirements03

Two independent device-tree bugs kept both Ethernet ports dead for a long time. They fail in different places for different reasons, and neither prints anything useful, so read this before editing the PHY nodes.

Both delay properties are mandatory

With phy-mode = "rgmii-id", dp83867_of_init() treats both ti,rx-internal-delay and ti,tx-internal-delay as required, and returns an error if either is absent. It reports that failure through pr_debug(), which is compiled out of a normal build, so nothing reaches the console. U-Boot simply says No ethernet found and Linux says Could not attach PHY (-19).

The PHY ID compatible must come first

Linux's fwnode_get_phy_id() reads only the first compatible string. If that string does not parse as ethernet-phy-idNNNN.NNNN, the node is registered as a plain mdio_device rather than a phy_device, and macb finds nothing behind the phandle. Putting the ID string first is the whole fix.

phy0: phy@0 {
    compatible = "ethernet-phy-id2000.a231", "ti,dp83867";  /* ID first */
    reg = <0x0>;
    ti,rx-internal-delay = <0x8>;   /* 2.25 ns — both mandatory */
    ti,tx-internal-delay = <0x8>;
    ti,fifo-depth = <0x1>;
};

Why 8

We picked the delay value by measurement rather than copying a reference design. Sweeping ti,tx-internal-delay across its range on this board, pinging the gateway at each setting, gives a clear plateau:

Value0248101214
Delay0.25 ns0.751.252.252.753.253.75
Result failfail passpass passpass pass

Ten of sixteen settings pass, so 8 sits comfortably mid-window. That width is worth noting on its own: it says the RGMII routing has real timing margin, because a marginal board gives you one lucky value rather than a plateau. Two other things agree with the choice — the DP83867 powers up at RGMIIDCTL = 0x77 (2.00 ns), one step away, and STRAP_STS2 reads 0x0100 on both PHYs, meaning the board straps no skew override and the value has to come from the device tree.

PHY addresses are 0 and 5

Not 0 and 1, whatever the schematic says. We confirmed this three independent ways: a full 0–31 MDIO scan, U-Boot's own probe, and each PHY's latched STRAP_STS1[4:0] register. Both PHYs sit on GEM1's MDIO bus (MIO76 and MIO77), and GEM2 reaches its PHY across that same bus — which is why the mdio node belongs under &gem1, not &gem2.

Networking04

Both ports run at line rate, so the SoC is not the limiting factor. Getting more than one port's worth of throughput out of a board, however, takes more than enabling bonding.

MeasurementResultConditions
Single port, TCP0.94 Gbps64 KB writes, 8 s, board → host
Link negotiation1000 / fullboth ports, U-Boot and Linux
Per-board ceiling~1.88 Gbpsboth links busy

Aggregation has two traps

Per-flow hashing. 802.3ad assigns each flow to one slave, so a single TCP connection is capped at one link's rate no matter how the switch is configured. To get past that you need more than one flow, so the DAQ daemon opens one connection per BRAM. The mapping is free: the PL already ping-pongs between the two buffers, so the traffic alternates between the links on its own.

Silent option fallback. Passing xmit_hash_policy and lacp_rate to ip link add does nothing on this kernel — the bond comes up layer2 and slow regardless. That is a quiet halving of your bandwidth, because layer2 hashes on MAC addresses alone, so every flow to the same server lands on the same slave and the second port carries nothing at all. NOTE: write these through sysfs after creating the bond and read them back to confirm. bond-setup.sh does both.

Do not bond into an unconfigured switch

With no LACP partner configured on the switch, the bond still comes up and still passes some traffic, which makes this easy to miss. But both slaves then transmit with the same MAC on two different switch ports, the switch sees that MAC flapping, and it starts dropping. In testing, traffic left the board fine while nothing could reach it, and SSH connected once before dying. That is worse than not bonding at all, which is why we leave the bond opt-in per board rather than bringing it up at boot.

Confirm before relying on it — you want a non-zero partner and two ports:

grep -E 'Partner Mac|Number of ports' /proc/net/bonding/bond0

DAQ interface05

Every memory-mapped block in the PL is exposed to userspace as a UIO device, so the readout software maps device memory with mmap() and handles interrupts with read() directly on the device node. No custom kernel driver is needed, which is the whole point of the arrangement.

FunctionAddressUIO nameNotes
BRAM 10xa0000000axi_bram_ctrl8 KB · 1024 × 64-bit words
BRAM 20xa0002000axi_bram_ctrlping-pong partner
READ_BUSY0xa0010000gpioPS → PL busy flag
WHICH_BRAM0xa0020000gpioPL → PS buffer select
TDC interrupt—tdc_intIRQ only, no memory map
Resolve by name, never by number

NOTE: UIO numbering is not stable. The four PS axi-pmon devices claim uio0 through uio3, so any hard-coded /dev/uioN path silently points your tool at a performance monitor instead of a BRAM. Match on /sys/class/uio/*/name, plus maps/map0/addr to tell the two BRAM controllers apart.

Data word

Each 64-bit BRAM word carries one hit:

Coarse timebits 38:11
Fine10:6
Channel5:0

Trigger and hit inputs arrive on PMOD1 — pin 1 is hit, pin 3 is trigger.

Readout sequence

  • Block on read() from the tdc_int UIO device
  • Raise READ_BUSY, read WHICH_BRAM to learn which buffer is full
  • Stream that BRAM out on the socket bound to it
  • Lower READ_BUSY and re-arm the interrupt

UIO nodes are world-accessible via a shipped udev rule, so the daemon runs unprivileged.

PCIe endpoint06

The card is a PS-PCIe endpoint by design: acquisition data buffers in the 4 GB of PS DDR4 before moving to the host, which is what the PS controller is good at. J4 is wired to the PS-GTR lanes and carries no GTH nets, so the PL transceivers are not an option without a board respin.

Every firmware precondition checks out on hardware and the link still does not come up. It is not hung, though, which took a while to establish — it cycles:

3000 samples of LTSSM (0xFD480228) across a host retrain

  2916   0x04   state 0   Detect.Quiet
    84   0x14   state 2   Polling.Active

Read that as a sequence: the card detects a receiver, enters Polling, transmits TS1 ordered sets, gets no reply, times out, and falls back to Detect — about 3 % duty cycle. Link training can be forced, which is how we got the measurement: toggling pcie_ctrl_reset (RST_FPD_TOP bit 17) is a PERST equivalent, and doing that while the host retrains its root port produces the excursions above.

Errata07

Three confirmed issues, followed by the things bring-up explicitly cleared. The second list is worth as much as the first: several of those were suspected at length, and recording that they are fine saves the next person from re-deriving it.

E1PHY address annotation is wrong (sheet 2/14)docs

The schematic annotates Ethernet B as ADDR = 0x1, but the silicon straps to 0x5. The DP83867 uses 4-level straps, where RX_D0 sets PHY_AD[1:0] and RX_D2 sets PHY_AD[3:2], so a single divider does not encode a single address bit. Harmless electrically; expensive in debugging time. The KiCad source should be corrected.

E2Strap divider R13/R14 has no BOM valuesdocs

The Ethernet B RX_D2 strap divider carries no value in the BOM or netlist — both show a bare R. Parts are clearly fitted, since the address reads back as 0x5, but the design files do not record what they are, which makes the board unbuildable from source as it stands.

E3PCIe TX pairs are not AC-coupledblocking

The card's transmit pairs (GTR_DPn_M2C, reaching J4 B14/B15 and the equivalent pins on the other lanes — the CEM PER pins) run direct with no series capacitors, while C15–C22 sit on the receive pairs where the host already provides coupling. UG1091 states that the K26 SOM adds no capacitors to the PS-GTR data lanes, and the PCIe CEM spec assigns transmit-side coupling to the add-in card. So these caps are ours to provide, and they are on the wrong pairs.

Mechanism consistent with the LTSSM evidence: a DC-coupled transmit pair drives the card's common-mode voltage straight into a host receiver that has no capacitor of its own, putting it outside its common-mode range so it cannot recover the bit stream. The card talks, the host cannot hear it, Polling times out.

Minimal test: fit 100 nF (0402) in series on the lane 0 transmit pair at J4 B14/B15 — two capacitors, enough for an x1 link. The prediction is specific enough to be wrong: the Polling.Active fraction should go from 3 % to 100 % and carry on through Configuration to L0. If it keeps cycling at 3 %, the transmit path is not the problem and the host-side adapter is the next suspect.

Cleared during bring-up

  • RGMII layout — ten of sixteen delay settings pass; wide margin
  • GTR pin mapping — M2C→PET, C2M→PER, refclk on A13/A14, all per CEM
  • MDIO topology — shared GEM1 bus works as designed
  • PHY part — DP83867 as drawn (ID 0x2000A231); early configs naming DP83869 were a software error
  • JTAG header — an early hardware-fault theory was wrong; the issue was tooling
  • QSPI, eMMC, power chain — repeated unattended cold boots, all solid

Open observation — warm reset

Warm reset hangs the board, reproducibly. We verified this with continuous serial capture: issuing reset from U-Boot, with the PL never loaded and Linux never run, prints resetting ... and then dies before any BootROM, FSBL or U-Boot output appears. Only a power cycle recovers it, and cold boots are entirely reliable.

The mechanism that fits every observation is that the boot-time QSPI driver leaves the flash in a volatile non-power-on state — 4-byte addressing, quad protocol, or both — which the BootROM does not expect on a warm reset. The same state explains why U-Boot's sf probe returns garbage JEDEC IDs. A candidate fix is patching the FSBL to issue a flash software reset after loading; until someone does, treat warm reset as unsupported.

Runbooks08

Build

The canonical build environment is the PetaLinux 2022.1 container on the build host. The XSA is not tracked in git, so drop it at Projects/vivado/TDC_64ch_2BRAM/TDC_64ch_2BRAM.xsa before you start. Worth knowing: PetaLinux 2022.1 accepts a Vivado 2025.2 XSA without complaint, so the tool versions do not have to match.

docker run --rm -v $HOME/SpinQuest-TDC-FW:/work -w /work/kernel \
  -u 1005:1005 -e HOME=/home/petalinux \
  -e BUILD_PETALINUX_ROOT=/opt/Xilinx/petalinux \
  --entrypoint /bin/bash docker_petalinux2:2022.1-04191534 -lc "make build"

All of the device-tree and kernel fixes described above live under kernel/configs/TDC_64ch_2BRAM/ and are copied into the generated project by the Makefile, so a fresh make build produces a correct image with no manual steps. That is deliberate — nobody should need to know this document's history to get a working board.

Netboot

Serve Image, system.dtb and the ramdisk over TFTP, then:

setenv ethact ethernet@ff0c0000
setenv ipaddr 192.168.0.180
setenv serverip <host>
tftpboot 0x18000000 Image
tftpboot 0x14000000 system.dtb
tftpboot 0x20000000 rootfs.cpio.gz.u-boot
setenv bootargs console=ttyPS1,115200 earlycon clk_ignore_unused \
    uio_pdrv_genirq.of_id=generic-uio,ui_pdrv cma=900M
booti 0x18000000 0x20000000 0x14000000

NOTE: serve these from a machine with a wired path to the board's switch. U-Boot's TCP stack does not survive a lossy Wi-Fi hop on a transfer the size of the rootfs; it fails part-way with queue overrun or a retry-count timeout.

Install to eMMC

Netboot the board first, then run kernel/flash_emmc.sh <board-ip> from the host. It partitions the eMMC over SSH and installs the current build: a 512 MB FAT32 boot partition and an ext4 root. Three target quirks are worth knowing if you modify it — busybox applets are not on root's PATH, dropbear provides no SFTP so files stream through cat, and sudo -S consumes stdin, which means anything piped through sudo has to be written unprivileged instead.

Boot script

NOTE: set the MAC addresses with env set -f, not plain setenv. U-Boot pre-sets a random, write-protected ethaddr during network init, so an ordinary setenv fails silently — and U-Boot's device-tree fixup then stamps that random MAC into the kernel's DT, overwriting even a local-mac-address baked into system.dtb. The -f is the whole fix.

House rules09

Each of these cost us something to learn. They are short because the reasons are documented above.

RuleReason
Always power cycle; never rebootWarm reset hangs before any output. Cold boots are 100 % reliable.
Never run saveenvThe U-Boot environment offset falls inside the BOOT.BIN region of QSPI.
Never devmem a PL address with the fabric unloadedWedges the AXI bus; recovers only on power cycle.
Avoid blind i2c probe sweepsThe K26 carries IRPS5401 PMICs on that bus.
Never power cycle during a flash writeLeaves QSPI in an unbootable state; recovery is JTAG only.

Register values here are live reads from a running board rather than quotes from a datasheet, and throughput figures are measured end to end. Corrections belong in ERRATA.md in the hardware repository and in this page together.
